# Handoff: write prompts for the library from a rough idea

## Goal

In marsad, a user writes a rough, vague idea for a standing instruction ("make Claude stop over-explaining in PRs"). marsad turns it into a high-quality prompt file using the best Claude model available through Claude Code. It shows the draft and anything that still needs the user's decision. The user edits or accepts it, and it is saved to their own prompt library. From then on it works exactly like the built-in prompts: it is listed in the `c` picker and in `marsad rules`, and works in both Normal session and Agent team mode.

Sharing prompts between users is out of scope. Keep the saved format a plain `.md` file so sharing can be added later without a migration.

## What already exists (v0.9.0, `src/rules.rs`)

- **The library** is `rules::library()`: the built-ins (`coordination`, `output-hygiene`), then each `.md` file in `<data dir>/prompts/` (`~/.claude/marsad/prompts/`; `MARSAD_HOME` overrides the data dir).
  - The file stem is the key.
  - The first `# ` heading is the title, and the first line of text is the summary.
  - Stems that clash with a built-in, equal `all`, or start with `-` are skipped.
  - The library is per user already, because it lives in that user's data dir. No account system is needed.
- **The `c` picker** (`app.rs` `RulesPicker`, `ui.rs` `draw_rules_picker`) has two steps: tick prompts, then choose Normal session or Agent team. It marks the user's own prompts "(yours)", and it scrolls.
- **Launch files** (`rules::ensure`) are written to `<data dir>/launch/` with hash names. A team gets a lead's file and a teammates' file. Teammates never see the lead's system prompt, which was verified in Claude Code 2.1.330.
- **Editor reuse:** the share view already hands text to `$EDITOR` through `Action::EditPost`. Reuse that flow to edit a draft.

## What to build

1. **The entry points:**
   - In the `c` picker, `n` starts "new prompt".
   - On a "(yours)" row, `e` edits that prompt and `d` deletes it after a confirmation.
   - CLI: `marsad prompt new [--from <file>]` reads the rough idea from the argument, the file, or stdin. Add `marsad prompt edit <key>` and `marsad prompt rm <key>`.
   - Built-ins can't be edited. Offer "save a copy to my library" instead, under a new key.
2. **Input:** a multi-line text box, or `$EDITOR`, for the rough idea, plus an optional name. Suggest a key slug from the title and refuse keys that clash.
3. **Generation:** run `claude -p` as a child process, off the UI thread, the same way the badge image is saved on its own thread. Show a spinner, and let `esc` cancel and kill the child process. Verify every flag against `claude --help` on the installed version before relying on it:
   ```
   claude -p --model opus --effort high --tools "" --max-turns 1 \
     --output-format json --json-schema '<schema>' --no-session-persistence \
     --append-system-prompt-file <data dir>/generator/<hash>.md
   ```
   - Send the rough idea on stdin, wrapped in `<rough_idea>…</rough_idea>`.
   - Make the model configurable (a `generator_model` setting, default `opus`). "Best model" means the strongest alias Claude Code accepts. The docs list `opus`, `sonnet`, `haiku` and `fable`, with no `best` alias. Check `claude --help` and pick the strongest. Fall back to the session default if the alias is rejected.
   - Read `structured_output` from the JSON. Fall back to `result` when it is missing.
   - Don't use `--bare`. It needs `ANTHROPIC_API_KEY`, and most users are on a subscription.
   - **Keep the user's context out of the run.**
     - Run it with the working directory set to a neutral folder, such as `<data dir>/generator/`, so that no project's CLAUDE.md is loaded.
     - Find out whether the user-level `~/.claude/CLAUDE.md` and the user's hooks still load. Use `--setting-sources` or `--settings` if they can be turned off.
     - marsad's own hooks will log this run as a session. Mark it, for example with an environment variable that `marsad hook` ignores, so it doesn't show up on the dashboard or in the usage stats.
   - Make it testable: let `MARSAD_CLAUDE` override the `claude` binary, so tests can point it at a stub script that prints canned JSON.
4. **The generator's system prompt** is a new bundled asset, `assets/PROMPT-GENERATOR.md`. It must be loaded together with `assets/OUTPUT-HYGIENE.md`, merged into one file, because `claude` reads only the last `--append-system-prompt-file`. Output hygiene matters twice here:
   - The rough idea is working context. The user's situation, names, projects and reasons must not leak into the generated rules unless they are the rule itself.
   - The generated prompt must not describe how it was produced. No "as requested", and no "generated by marsad".
5. **The review screen:**
   - It shows the draft rendered as markdown, a short "what I assumed" list, and "questions for you" (the open decisions the rough idea left).
   - Actions:
     - `enter` saves.
     - `e` opens the draft in `$EDITOR`.
     - `r` regenerates with a line of feedback. The previous draft and the feedback go back into the same generator call.
     - `esc` discards.
   - Answering a question can be a regenerate with the answer as feedback.
6. **Save:**
   - Write `<data dir>/prompts/<key>.md` atomically (write to a temp file, then rename, like `write_if_changed`).
   - Refresh the picker's library.
   - Tick the new prompt.

## The JSON schema to ask for

```json
{
  "type": "object",
  "required": ["key", "title", "summary", "body", "assumptions", "questions"],
  "properties": {
    "key": { "type": "string", "pattern": "^[a-z0-9][a-z0-9-]{1,40}$" },
    "title": { "type": "string" },
    "summary": { "type": "string", "description": "one line, at most 80 characters" },
    "body": { "type": "string", "description": "the whole file, starting with '# <title>'" },
    "assumptions": { "type": "array", "items": { "type": "string" } },
    "questions": { "type": "array", "items": { "type": "string" } }
  }
}
```

The body's first line must be `# <title>` and its first paragraph the summary, so the library reads it back the same way.

## What makes a good standing prompt: rules for PROMPT-GENERATOR.md

Write the generator's own prompt by these rules, and tell it to write its output by them. They come from Anthropic's prompting best practices (`platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices`) and from Claude Code's memory guide (`code.claude.com/docs/en/memory`). Re-read both before writing the asset.

1. **Be explicit about the behavior.** Write "Write the summary as flowing prose", not "Can you make it nicer". Every rule should be checkable. Replace vague rules like "format code properly" or "test your changes" with concrete ones like "run `cargo test` before committing".
2. **Give the reason for each rule.** "Answers are read aloud, so avoid ellipses" lets the model generalize, where a bare "NEVER use ellipses" doesn't.
3. **Use normal emphasis.** Avoid ALL-CAPS and "CRITICAL / MUST". Current models follow the system prompt closely, and shouting causes overtriggering.
4. **Say what to do, not only what not to do.** For example: "write prose paragraphs" rather than "no markdown".
5. **Match the prompt's style to the output you want.** A prompt written in heavy markdown gets heavy markdown back.
6. **State whether Claude should act or advise by default,** when the rule touches that.
7. **Use examples only when they help, and make them match the behavior you want.** Use 3–5 varied examples in `<example>` tags. A single example gets copied too closely.
8. **Keep it short and structured.** Use headings and bullets, keep well under 200 lines (aim for fewer than 60), and use one idea per bullet.
9. **Make sure no two rules contradict each other.** When they do, the model picks one arbitrarily.
10. **Leave out what Claude can work out from the code** (layouts and dependency lists). Keep conventions, pitfalls and the reasons behind them.
11. **Keep standing rules out of procedures.** A long step-by-step procedure belongs in a skill. Anything that must happen every time belongs in a hook, because a prompt is context, not an enforced setting. Have the generator flag this in `questions` instead of forcing it into the prompt.
12. **Give a one-sentence role only when it adds something.**
13. **Write for both the lead and teammates.** A library prompt may be handed to agent-team teammates. It must make sense to a reader who has no other context: no "as discussed" and no references to a conversation.

The generator should also:
- put the rough idea after its instructions, inside tags
- keep the user's intent and never add rules the user didn't imply; it lists what it inferred under `assumptions`
- ask in `questions`, rather than guess, when a choice changes behavior (for example: should it apply to commits only, or to all docs?)

## How to verify

- **Unit tests:**
  - the command and its arguments are built correctly
  - parsing works for `structured_output`, falls back to `result`, and handles bad JSON
  - key slugs are made correctly, and clashes and `-`-prefixed keys are refused
  - saving is atomic
  - editing or deleting a built-in is refused
  - the generator's prompt file is the generator text plus output hygiene, in that order
- **A stub `MARSAD_CLAUDE` script** for the TUI flow: new prompt, review, regenerate, save, then the prompt shows up in the picker as "(yours)".
- **One live run** with the real `claude`. Give it a vague idea that contains personal details, such as "I'm at a nonprofit, my boss Sam hates long PRs". Check that the saved prompt has no names, no employer and no story, only the rule.
- **Launch a session from the saved prompt,** in both Normal and Agent team mode. Check that it's applied, using the codeword-probe method in tmux from v0.9.0.

## Repo conventions

- Work on a branch off `origin/main` and open a PR into `main`. CI runs `cargo test --locked` on Ubuntu, macOS and Windows.
- Release with a `chore/release-x.y.z` PR that bumps `Cargo.toml`, `Cargo.lock` and `CHANGELOG.md` (short user-facing bullets). Then push the `vX.Y.Z` tag, which runs the dist release workflow, and open a `chore: sync develop with main` PR.
- The repo isn't formatted with a single rustfmt config. Format only the lines you change; don't run `cargo fmt` on the whole repo.
- Update `README.md`, `assets/SKILL.md` and `CONCEPTS.md` for the new commands and keys.
